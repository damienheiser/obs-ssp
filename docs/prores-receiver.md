Status: implemented, built and installed locally; production parser/decode verified against actual9/20-frame captures. ## Requirement and mechanism

The operator clarified that this task owns the receiver for the camera agent's native ProRes sender. Existing camera reception is retained. The receiver accepts declared codec1006 and complete standard length-framed `icpf` ProRes frames through the existing SSP video packet and IPC callbacks. No encoder/firmware patch or synthetic camera service is introduced. Actual Trial12 packets use wiretype0x6f, frame_type5, base17bytes plus the observed20byte extension; the production parser returns the exact compressed payload and microsecond PTS. No new packet type is inferred from an internal camera producer enum.

The original generic ProRes decoder used automatic frame threading. The first actual C4K frame was buffered rather than returned, so a short native burst could produce no displayed frame until EOF/flush. ProRes now uses at most four slice threads with a33,554,432pixel bound. As an intra-only codec it needs no inter-frame reordering. Each recorded access unit returns an immediate I21010bit4:2:2 frame with exact dimensions/PTS, without EOF flushing. Existing AVC/HEVC decoder defaults remain unchanged. The source already disables hardware decoding for ProRes even when its hardware-acceleration property is enabled.

Declared codec1006 is recognized in metadata. For actual payload detection, complete `icpf` length framing must match the provided byte count; malformed/truncated declarations are rejected. Generic ProRes payload sniffing remains additive for existing senders. The initial receiver had a4MiB packet admission cap; this is now32MiB with bounded queue/IPC handling (the camera server's maximum remains unmeasured); Trial12 payloads are1,240,112–1,257,076bytes. The codec detector additionally caps accepted ProRes buffers at32MiB for other existing ingress paths. No full4K-HQ/4444/12bit/RAW or arbitrary sender framing claim follows from these bounds.

## Explicit 12-bit decoder descriptor — host fixture only

An actual private host-generated ap4h/4444 MOV fixture was SHA-verified and its compressed access unit extracted without re-encoding. The raw decoder without a codec tag produced AVYUV444P10LE; mapping I412 alone failed, correctly exposing lost precision. The new `ffmpeg_decode_prores_init` requires a validated FourCC/depth pair before opening the codec: ap4h/ap4x with12, or apco/apcs/apcn/apch with10. Missing/unknown/mismatched pairs reject before allocation. Legacy initializers still pass0/0 and retain existing behavior. ProRes remains software, at most4slice threads and32MP.

With explicit ap4h/12, the actual one-frame4096x2160 fixture decodes immediately as AVYUV444P12LE -> OBSI412, preserves PTS, has three full-resolution16-bit-storage/right-aligned12-bit planes and no alpha. Plane values stay<=4095. This qualifies a decode primitive, not camera encoding, live12-bit SSP, alpha, calibration or real-time capability. Independent focused descriptor review found no concrete issue and did not read the private fixture or run tests. Full18selected offline CTests pass7.29s; syntheticcameraIPC remains excluded. Universal normal build and formatting pass.

The original packet/queue gap is now resolved by the32MiB admission and64MiB/32-packet resident budget below. Existing native/peer manifests still do not transport the tag/depth/profile descriptor into this initializer, so live12-bit reception is not enabled by these budget changes. Producer codec1006 alone cannot distinguish42210 from44412. The future format contract must drive decoder initialization and fail closed when required precision metadata is absent; an old receiver must not silently accept a new format and down-label it.

Color evidence also disagrees: source converter declares a full-rangeBT709YCbCr transform with unknown primaries/transfer, while unmodified ffprobe's stream and decoded frame report TV/limited range and no primaries/transfer/matrix fields. The decode test uses existing DEFAULTcolor behavior and makes no color-accuracy claim or invented OETF/calibration. Preserve these distinct facts in the descriptor rather than silently equating them. Bayer has no OBSvideo_format; RAW needs explicit CFA/packing/stride/validbits/calibration and an actual demosaic stage.
