# OBS peer SSP transport

The operator authorizes first-class OBS sender/receiver streaming, multiple video and audio tracks, obs-websocket controls/authentication and capability-driven UI. Existing camera SSP remains additive and unchanged. This concern has its own branch and task; no firmware capabilities are inferred.

The peer transport uses SSP length-prefixed TCP frames with an explicit OSSP version1 handshake, separate from legacy camera authentication. A fresh cryptographically generated challenge authenticates both ends through domain-separated HMAC-SHA256 with a separate generated256bit media key; no secret enters process arguments or logs. Default bind is loopback, remote bind is explicit; this transport does not encrypt media and is intended for trusted LAN/VPN use. Standard obs-websocket authentication protects its normal controls; no second WebSocket server is added.

A versioned manifest describes only attached real OBS encoders, stable per-kind track indices, codec configuration, dimensions, exact FPS, sample rate and channels. Multiple video/audio tracks are carried with independent indices and microsecond PTS/DTS. A receiver source selects one advertised video/audio pair; multiple sources can select different pairs without mixing identities. Camera HTTP controls never run for peer sources. Initial supported encoded media is AVC/HEVC/regular ProRes and AAC/PCM where actual encoders/decoders are available; unsupported codecs remain unavailable. This does not implement ProResRAW or ZRaw framing.

Bounds: at most four clients, authentication deadline5s, maximum16MiB packet,64KiB codec configuration, bounded512packet/32MiB sender queue and16MiB per-client pending writes. Invalid manifests/indices/sizes fail closed before decoding. A lagging client disconnects rather than retaining an unbounded queue or corrupting prediction chains; late join waits for a keyframe per video track. Stop cancels sockets, joins owned threads and preserves unrelated OBS state.

Verification is through actual OBS renderer, two real video encoders at distinct resolutions/cadences and two real audio encoder tracks fed distinct tones, production server/client connections, actual decoding, wrong-secret rejection, late join and cancellation/backpressure. Unit bounds tests do not substitute for media observations. A single independent security review follows implementation. Recovery: stop peer output, remove peer sources, restore the prior signed plugin backup; existing camera source/configuration remain intact. No listener or successful decode is claimed until observed tests pass.
